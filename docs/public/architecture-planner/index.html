03 · Separação

Onde cada responsabilidade deve rodar.

GKE, serverless, VPS e storage não são alternativas equivalentes. Cada um resolve um perfil de carga diferente.

VPS

VPS / VM

Melhor ponto de partida para carga previsível, equipe pequena e necessidade de controlar mTLS e rede.

  • Gateway e workers no início
  • Docker Compose reproduzível
  • IP estável e troubleshooting simples
  • Não concentre banco, anexos e chaves globais na mesma VM
Ideal: 0–100
GKE

GKE / Kubernetes

Entra quando há múltiplos workers, HPA, filas particionadas, zonas e deploy independente.

  • P2P ingress stateless
  • Send workers escaláveis
  • Relayers e indexadores isolados
  • Não use para esconder um monólito sem observabilidade
Ideal: 500+
ƒ()

Serverless

Ótimo para interfaces, webhooks e APIs esporádicas; inadequado para tudo que exige conexão duradoura.

  • Webmail e Dashboard estáticos
  • Webhooks de Payment
  • Admin API de baixa frequência
  • Evite P2P mTLS, watchers WebSocket e workers contínuos
Complementar
S3

Storage gerenciado

É uma camada própria: objetos, dados relacionais, cache e segredos possuem durabilidade diferente.

  • S3/R2 para anexos e backups
  • Postgres HA para metadados
  • Redis para cache e filas descartáveis
  • Segredos ficam em KMS/HSM, nunca em bucket ou banco

04 · Federação

Open source local. Confiança global consumida.

O nó soberano continua dono dos e-mails, caixas, chaves de domínio e infraestrutura. Apenas operações globais de confiança atravessam a fronteira do oráculo.

Oráculo central

Serviço global isolado, com HSM/KMS, política de rate limit e trilha de auditoria. Não recebe acesso administrativo ao nó.

Provas de domínioAtesta posse após desafio DNS e regras anti-replay.

Regra de segurança: o pacote open source nunca contém oracleSignerPrivateKey, autoridade de upgrade global ou credenciais de tesouraria. Se o oráculo cair, novas provas, mirrors e julgamentos aguardam; a entrega P2P normal deve continuar com estado finalizado em cache.

06 · Execução

O caminho realista a partir do código atual.

A ordem reduz risco e custo. Cada etapa cria a condição operacional necessária para a próxima.

Agora · fundação

1. Tornar o básico substituível

  1. Extrair o oráculo do processo do Gateway e definir API autenticada.
  2. Trocar anexos locais por interface S3/R2/MinIO com URLs pré-assinadas.
  3. Formalizar jobs de envio, relayer e indexação com idempotência e DLQ.
  4. Segregar segredos de domínio, relayer, oracle e upgrade.
Depois · 101–2.000

2. Escalar processos, não o monólito

  1. Separar P2P ingress e responder 202 após validação mínima.
  2. Escalar send workers por profundidade da fila e latência.
  3. Adotar Postgres HA, Redis gerenciado e object storage.
  4. Medir SLOs por rota crítica, tenant e região.
Maturidade · 2.000+

3. Regionalizar e limitar blast radius

  1. Criar células regionais de Gateway, fila e storage.
  2. Particionar tenants com roteamento determinístico.
  3. Executar canário on-chain e failover de RPC contínuos.
  4. Evoluir o oráculo de chave única para multisig/TSS.
Leitura honesta do estado atual: o repositório já possui Gateway, WebMaivw, Dashboard, Payment, Console, Postgres e Redis; porém as rotas do oráculo ainda vivem no Gateway e os anexos usam filesystem/Base64. A página descreve a estrutura-alvo e marca essas duas extrações como trabalho necessário — não como capacidade já entregue. As estimativas são parâmetros de planejamento, não benchmark nem promessa de SLO.
